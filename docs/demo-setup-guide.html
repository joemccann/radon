Provision the Hetzner VM Hetzner

a fresh box for the isolated demo stack
✓
  1. In Hetzner Cloud Console → your project → Add Server.
  2. Location: same region as your prod ib-gateway VM (lowest latency to Turso/UW). Image: Ubuntu 24.04. Type: CPX21 (3 vCPU / 4 GB) is plenty for a demo; CPX31 if you expect many concurrent users.
  3. Add your SSH key. Name it radon-demo. Create.
  4. Copy the new public IPv4. SSH in and install Docker + compose plugin:
ssh root@<NEW_VM_IP> curl -fsSL https://get.docker.com | sh apt-get install -y docker-compose-plugin useradd -m -s /bin/bash radon && usermod -aG docker radon
Do NOT join this VM to the Tailscale tailnet that reaches ib-gateway:4001, and do not run an IB Gateway container on it. IB must be physically unreachable. I will provide the demo docker-compose.yml (Next.js + FastAPI in RADON_API_TEST_MODE=1 + relay + Caddy) — you do not build it.

Deploy the demo frontend on Vercel Vercel

demo.radon.run frontend + edge firewall / DDoS / IP rate-limiting
✓
Architecture: the demo frontend (the web/ Next.js app) runs on Vercel as demo.radon.run — same platform as radon.run — so Vercel gives us the edge WAF, DDoS, and IP rate-limiting for free. The FastAPI + relay backend stays on the isolated Hetzner VM from step 1. The Vercel frontend calls the VM's FastAPI over the public internet, so the backend authenticates the Clerk JWT (no localhost trust bypass) — a security upgrade I wire on my side.
  1. The joemccann/radon repo is already connected to Vercel (it backs the marketing-site project, root site/). In Vercel → Add New → Project → pick the existing joemccann/radon repo and create a second project from it with Root Directory = web/. One repo backs multiple Vercel projects, each with its own root + domain. Framework: Next.js.
  2. Settings → Domains: add demo.radon.run (Vercel manages DNS + TLS since radon.run is already a Vercel domain — no A record / Cloudflare needed).
  3. Settings → Git: set the Production Branch to a dedicated demo branch (so demo deploys are independent of prod main), or use an Ignored Build Step scoped to web/. I'll confirm the exact gating when wiring.
  4. Settings → Firewall: enable Vercel WAF (managed OWASP ruleset), add Rate Limiting rules (e.g. challenge at 100 req/min/IP, block at 1000/min/IP), and turn on Attack Challenge Mode readiness for DDoS. This replaces the old Cloudflare layer.
  5. Settings → Environment Variables (Production): I'll hand you the exact list when wiring — it points the frontend at the VM backend (RADON_API_URL → the VM's public FastAPI URL) and carries the demo Clerk role, demo Turso, Upstash, and demo AI keys. Leave this until I send the list.
Don't deploy to production yet — create the project + attach the domain + firewall, but hold the first prod deploy until I've added the demo-mode code (Phase 2) and given you the env vars, so demo.radon.run never goes live pointing at the wrong backend.
Send me: the Vercel project name/URL + confirm demo.radon.run is attached and the Firewall + rate-limit rules are on. (The backend RADON_API_URL I derive from the VM.)

demo data physically apart from the prod journal/account
✓

turso db create radon-demo --location lax turso db show radon-demo --url turso db tokens create radon-demo
  • db show --url prints the libsql:// URL.
  • tokens create prints the auth token.
  • I will run the migrations + demo_seed.py against this DB — you just create it + hand me the URL/token.
Critical: this must be a brand-new DB, never the prod radon-joemccann URL. The prod portfolio/journal/orders tables have no user_id, so a shared DB would leak your real positions.
